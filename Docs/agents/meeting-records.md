# 会议记录提交流程

会议记录固定复用 `li/docs-meetings`，日常编辑和提交都在同一个 Unity 工程目录中完成。流程为更新会议分支、创建或更新 PR、由班审查并合并到 `main`。合并后保留该分支，下一次继续使用。

## 操作步骤

1. 用户在 Unity 工程的 `Docs/会议记录/` 中用 Word 新建、编辑会议纪要，保存后请求发布。
2. 提交前记录当前分支和 `git status`，分别检查已暂存、未暂存与未跟踪的改动。为本次会议文件保存一份工作目录之外的临时备份，避免切换到旧分支时覆盖刚编辑的内容。
3. 非会议开发改动保留在原所属分支。若它们会阻止切换或混入会议提交，先安全保存这些改动及其暂存状态，例如使用限定文件范围的 stash。无法安全分离时先说明情况并询问用户，禁止丢弃、覆盖或顺手提交；也不自动另建 worktree。
4. 在同一个工程目录切换到 `li/docs-meetings`，获取远端状态并确认现有 PR。上一条 PR 已合并时，快进或正常合并最新 `origin/main`，保留已发布历史，避免 reset 或强制推送。
5. 确认 `Docs/会议记录/` 中是本次最新保存的文件，需要时从临时备份恢复；检查 DOCX 完整性，更新 `Docs/CHANGELOG.md`，仅暂存会议文件与对应说明，检查差异后提交并推送。
6. 有未合并 PR 时追加到同一 PR；没有时从固定会议分支向 `main` 创建正式 PR，写明会议日期、改动和文件检查结果。
7. 如临时保存了非会议改动，回到其原所属分支恢复原内容与暂存状态，并告知用户最终停留的分支和改动状态。
8. 班审核并合并后，用户在本地切回 `main`，执行 `git pull --ff-only origin main`。固定会议分支保留，后续继续复用。

如果固定分支被误删，在最新主线上恢复同名分支，不再创建新的日期分支。Issue 操作仍遵循 `AGENTS.md` 的明确授权规则。

分支共享同一个仓库，无需移动分支目录；切换分支会让工作目录显示该分支对应的文件版本。默认不再为会议记录保留独立 worktree。
